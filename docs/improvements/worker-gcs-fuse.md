# Cloud Storage FUSE によるワーカーの効率化

LLM Worker (Cloud Run) において、Google Cloud Storage (GCS) をローカルファイルシステムとしてマウントする設計案。

## 概要
Cloud Run の [Cloud Storage FUSE](https://cloud.google.com/run/docs/configuring/services/cloud-storage-fuse) 機能を使用し、GCS バケットを `/mnt/gcs` 等にマウントする。これにより、ワーカーが GCS 上のドキュメントを直接ローカルファイルとして扱えるようにする。

## メリット
- **既存ツールの活用:** `grep` や `find`、あるいは標準的なファイル I/O を使うライブラリをそのまま GCS 上のデータに対して利用できる。
- **実装の簡略化:** GCS クライアント SDK を使った明示的なダウンロード処理（および `/tmp` 管理）が不要になる。
- **メモリ節約:** `/tmp` は tmpfs（メモリ）であるため、巨大なファイルをダウンロードすると OOM の原因になるが、FUSE マウント経由であればメモリ消費を抑えつつストリーミング的に読み込める。

## ユースケース
- **高速全文検索:** `grep` による簡易検索と、その結果のキャッシュによる再利用。
- **マルチドキュメント処理:** 大量の参考資料を一度に参照する際、必要な部分だけをオンデマンドで読み込む。

## 注意点
- **ステートレス性:** Cloud Run インスタンスが終了するとマウントも解除される。インデックスなどを永続化したい場合は、明示的に書き出しが必要。
- **レイテンシ:** ローカルディスクに比べると I/O レイテンシが発生する。
- **設定:** Terraform または `gcloud` コマンドでのバケットマウント設定が必要。

## ディレクトリ構造 (FUSE マウント時)

`/mnt/gcs` にバケットをマウントした場合のディレクトリ構成案。

zip アップロードされたドキュメントは展開後にディレクトリとして格納される：

```text
/mnt/gcs/
├── {workspace_id}/
│   ├── {document_id}                # 単一ファイルのドキュメント (ReadOnly)
│   └── {document_id}/               # zip 展開後のドキュメント (ReadOnly)
│       ├── report.txt
│       └── appendix/
│           └── contract.txt
└── .cache/
    └── v1/                          # キャッシュスキーマバージョン
        └── {document_id}/
            └── {doc_hash}/          # コンテンツハッシュによる世代管理
                └── grep/
                    └── {pattern_hash}.json  # grep 結果のキャッシュ
```

## 保存方法の Contract (契約)

キャッシュの整合性と寿命を担保するため、以下のルールを適用する。

### 1. 世代管理 (Invalidation)
- パスに `{doc_hash}` を含めることで、同じドキュメント ID でも内容が更新された場合は自動的に新しいパスが使用される。
- 古いハッシュのディレクトリは GCS のライフサイクルルール（例：30日未アクセスで削除）によって自動消滅させる。
- zip ドキュメントの `doc_hash` は zip ファイル自体のハッシュとする。

### 2. キー生成ルール
- **pattern_hash**: `sha256(pattern + context_lines_count)`
  - 検索パターンと周辺行数の設定が同じであればヒットさせる。
- **doc_hash**: ドキュメントアップロード時に計算されるコンテンツの SHA-256。

### 3. 書き込みの原子性 (Atomicity)
- FUSE 経由での書き込みは、一度 `{filename}.tmp` に書き込みを完了させてから `rename` を行う。
- これにより、他のワーカーが書き込み途中の不完全なキャッシュを読み込むことを防ぐ。

### 4. 読み込み戦略 (Read-Through)
- ワーカーはまずキャッシュパスを確認し、存在しなければツール（grep等）を実行して結果をキャッシュに書き込む。
- ドキュメント全体を事前にコピーするのではなく、必要なキャッシュエントリのみをオンデマンドで生成・取得する。これにより Cold Start を抑え、FUSE の「必要な部分だけ読む」利点を活かす。

### 5. grep キャッシュのスキーマ (`{pattern_hash}.json`)

```json
{
  "pattern": "契約解除",
  "context_lines": 10,
  "matches": [
    {
      "file_path": "appendix/contract.txt",
      "line_number": 142,
      "line": "第10条 契約解除について定める。",
      "before": ["第9条 ...", "..."],
      "after":  ["解除の申し出は...", "..."]
    }
  ],
  "created_at": "2026-05-07T09:00:00Z"
}
```

- `file_path` は `{document_id}/` からの相対パス。単一ファイルの場合はファイル名のみ。
- `context_lines` は固定値（デフォルト10）。追加取得は行わず、文脈が足りない場合は `extract_text` で該当箇所全体を読む。
- `matches` が空配列の場合もキャッシュとして保存し、同じパターンで再度 grep が走らないようにする。

## FUSE を活用する ADK ツール定義

GCS FUSE のマウントを前提とした、具体的な ADK ツールの役割と動作仕様。

### 1. `grep_search` (新規)
ドキュメント全体を LLM に読ませる前に、特定のキーワードでアタリをつけるためのツール。

- **役割**: 指定されたキーワードでファイルを grep し、マッチした行とその前後（Context）を返す。
- **実装**: `exec.Command("grep", "-r", ...)` を実行（zip展開後のディレクトリにも対応）。結果を `.cache/v1/.../grep/` に保存。
- **LLM のメリット**: 数百ページのドキュメントから「契約解除条項」などの特定箇所をピンポイントで、かつ低コスト・高速に取得できる。
- **前提**: テキスト変換済みのファイルを対象とする。PDF 等のバイナリファイルには直接適用しない。

### 2. `extract_text` (既存の最適化)
現在、ファイル全体をメモリにロードしている処理を、FUSE 経由のストリーミングに置き換える。

- **改善点**: `http.Get` + `io.ReadAll` から、`os.Open` + `io.Copy` (またはバッファリング読み込み) へ。
- **メリット**: 巨大な PDF やテキストファイルでも Cloud Run のメモリ制限 (OOM) を気にせず処理可能になる。

## zip ドキュメント対応に伴うアーキテクチャの見直し

現在の実装は単一ファイルのアップロードを前提としており、zip に対応するには以下の処理が新たに必要になる。

### 必要な処理

1. **zip 展開**: アップロード時に zip を展開し、`{document_id}/` ディレクトリとして GCS に格納する。
2. **ファイル種別ごとのテキスト変換**: 展開後のファイルは PDF・画像・テキスト等が混在する可能性があり、種別に応じた変換処理が必要。
   - テキスト系 (`.txt`, `.md`, etc.): そのまま利用
   - PDF: テキスト抽出
   - 画像・音声・動画: LLM による説明生成、または音声認識による文字起こし
     - 詳細は [multimedia-processing-transcription.md](multimedia-processing-transcription.md) を参照。

### Worker の統合 vs 分離

テキスト変換処理を別 Worker として分離する案も考えられるが、**現時点では LLM Worker に統合する**方針をとる。

**分離案のデメリット:**
- PubSub 等のキュー管理が必要になり、インフラ複雑度が上がる
- 「変換完了後に LLM Worker が動く」という非同期依存が生まれ、エラーハンドリングが難しくなる

**統合案のメリット:**
- Cloud Run 1種類で完結し、シンプルに保てる
- 現在のスループット要件では十分
- 将来的に分離が必要になっても、処理の境界を意識して実装しておけば切り出しは容易

### 既存実装で見直すべき箇所

- `extract_text` ツール: 単一ファイルを前提とした実装をディレクトリにも対応させる
- ドキュメントアップロード処理: zip 判定 → 展開 → GCS への配置フローの追加
- `doc_hash` の計算: zip の場合は zip ファイル自体のハッシュを使う（展開後ファイル群のハッシュは不要）

## 既知の落とし穴と対策

### 1. FUSE の atomic rename は POSIX 準拠でない

GCS FUSE の `rename` は内部的にコピー＆削除として実装されており、真の atomic ではない。複数ワーカーが同一パスへ同時に書き込む（cache miss が並行して発生する）場合、不完全なファイルが残るリスクがある。

**対策: Last-writer-wins を許容する設計にする**

同一 `{doc_hash}` に対してキャッシュの内容は決定的（同じ入力なら同じ出力）なので、複数ワーカーが同時に書き込んでも結果は等価になる。atomic 性を強制するより、**競合は許容して上書きさせる**設計の方がシンプルで現実的。

- `{filename}.tmp` → `rename` のパターンは引き続き行う（部分書き込みの読み込みを防ぐ最低限の対策）
- 読み込み側は `.tmp` ファイルをキャッシュヒットとして扱わないようにする

### 2. キャッシュと原本を同一バケットに置く場合の IAM 設計

原本ドキュメント（`{workspace_id}/`）は ReadOnly、キャッシュ（`.cache/`）はワーカーが書き込む。同一バケット内でこの権限を分けるには IAM Conditions が必要になり複雑。

**対策案:**
- **バケット分離（推奨）:** `synthify-documents`（原本、ReadOnly）と `synthify-cache`（キャッシュ、ReadWrite）の2バケット構成にする。FUSE は2つをそれぞれ別パスにマウントする。
- **プレフィックス IAM（簡易）:** 単一バケットのまま、Cloud Run の SA に対して `.cache/` プレフィックスのみ `storage.objects.create` を許可する IAM Condition を設定する。

## データベース (PostgreSQL) からの `LIKE` 検索廃止

GCS FUSE による検索のオフロードに伴い、DB 層での全文検索 (`LIKE` クエリ) を廃止する。

### 廃止対象のクエリ例
- `SearchWorkspaceDocumentChunksByText`: `LOWER(heading || ' ' || text) LIKE $1` による部分一致検索。

### DB 検索のコストと課題

1. **計算コスト (CPU/IO):**
   - **フルスキャン:** `LIKE '%pattern%'` のような中間一致検索は B-Tree インデックスが効かないため、全チャンク行の `O(N)` スキャンが発生する。
   - **文字列結合のオーバーヘッド:** `heading || ' ' || text` のように実行時に文字列を結合して検索する場合、毎クエリで CPU リソースを大量に消費する。
   - **メモリ圧迫:** 大量のテキストデータを DB のバッファキャッシュに読み込む必要があり、他の重要なメタデータクエリのパフォーマンスを阻害する。

2. **空間コスト (Storage):**
   - **DB の肥大化:** 全文検索のために全テキストを DB に保存し続けると、データベースのサイズが増大し、バックアップやリストアの時間が長くなる。
   - **インデックス効率:** PostgreSQL で `pg_trgm` 等のインデックスを張ることも可能だが、インデックスサイズ自体がテーブルサイズを超えることがあり、ストレージコストを押し上げる。

### GCS FUSE 移行後の改善

- **コストのオフロード:** 検索処理は Worker の CPU / メモリで行われ、DB は関与しない。
- **スケーラビリティ:** ドキュメント数が増えても DB のパフォーマンスに影響を与えない。
