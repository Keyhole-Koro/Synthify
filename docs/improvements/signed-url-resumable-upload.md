# 署名付きURLと再開可能アップロードの導入計画

## 目的
本番環境におけるセキュリティの確保と、GB級の大容量ファイルの安定したアップロードを実現するため、現在のアップロード方式を署名付きURL（Signed URL）および正式な再開可能アップロード（Resumable Upload）へと移行する。

---

## 1. 現状と課題

### 1.1 現状の構成
- **ローカル環境:** GCSエミュレータに対して認証なしの直接URLを発行。
- **プロトコル:** バックエンドがGCS APIに対してセッションを開始し、フロントエンドにセッションURLを返却、フロントエンドが `PUT` で送信。

### 1.2 課題
- **本番環境のセキュリティ:** 本番のGCSバケットは非公開にする必要があるため、認証なしのURLは利用できない。
- **大容量ファイルへの耐性:** 現在の「一括PUT」では、ネットワーク断絶時に最初からやり直しになるリスクがある。

---

## 2. 改善後のアーキテクチャ

### 2.1 署名付きURL (Signed URL) の採用
バックエンドの `DocumentUploadURLBuilder` を、GCS SDK を利用した署名付きURL生成ロジックに差し替える。

- **セキュリティ:** 特定のユーザー、特定のオブジェクト、特定の期間（TTL）に対してのみ書き込みを許可する。
- **透過性:** フロントエンドは現在と同様に「返ってきたURLに `PUT` する」だけでよいため、フロントエンド側の変更は不要。

### 2.2 Resumable Upload の最適化
Resumable Upload プロトコルを正式に運用し、大容量ファイルに対応する。

- **チャンク分割送信:** フロントエンド側でファイルを数MB単位のチャンクに分割して送信し、各チャンクの成功を確認しながら進める実装への拡張。
- **再開ロジック:** 送信が中断された場合、`PUT` リクエストに `Content-Range: bytes */size` を含めて現在の保存状況をストレージに問い合わせ、未送信分から再開する。

---

## 3. 移行ステップ

### Phase 1: インターフェースの維持（完了済み）
- バックエンドがURLを発行し、フロントエンドが `PUT` を使う構造を確立。

### Phase 2: 本番用 Generator の実装
- `packages/shared/app/bootstrap.go` において、本番環境（`ENV=prod`）の場合に `cloud.google.com/go/storage` を使用して署名付きURLを発行する実装を追加する。

### Phase 3: フロントエンドの大容量ファイル対応
- `apps/web` において、ファイルサイズが一定以上（例：100MB以上）の場合に自動的にチャンク分割送信を行うロジックを導入する。

---

## 4. 検討事項

- **署名の有効期限 (TTL):** 大容量ファイルのアップロード時間を考慮しつつ、セキュリティを損なわない時間（15分〜60分程度）の設定。
- **CORS設定:** 本番のGCSバケットにおいて、アプリケーションのドメインからの `PUT` および `POST`（セッション開始時）を許可するCORSポリシーの適用。
- **S3互換性:** 将来的にAWS S3等を利用する場合、V4署名（SigV4）への対応が必要になる。
