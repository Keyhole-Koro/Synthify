## 1. SQL クエリの可観測性

### 改善案
- **SQLラッパーの導入**: `sql.DB` を直接使うのではなく、クエリ実行時間やパラメータを自動的にログ出力する。
  - 実装候補: `jackc/pgx` の `QueryTracer` または `otelsql` (OpenTelemetry integration)。
- **スロークエリの検知**: 200ms 以上かかったクエリを `WARNING` レベルでログ出力し、実行計画を `EXPLAIN` するためのヒントにする。
- **コネクションプールの監視**: 空きコネクション数や待ち時間を定期的にメトリクスとして出力し、スケーリングの判断材料にする。

## 2. Gemini API 呼び出しの可観測性とコスト管理

### 現状
- `llm/gemini.go` でモデル名と実行時間のみがログ出力されている。

### 改善案
- **トークン使用量の記録**:
  - `UsageMetadata` (Prompt/Candidates/Total tokens) を全ての LLM レスポンスから抽出し、`joblog` または専用の監査テーブルに保存する。
- **コスト計算の自動化**:
  - トークン量とモデル単価から、ジョブごとの概算コスト（USD/JPY）を自動計算し、管理画面で表示可能にする。
- **リクエスト/レスポンスのダンプ**:
  - `LOG_LLM_PAYLOAD=true` 環境変数がある場合、プロンプトと生成結果の全文を JSON で出力する（デバッグ用）。
- **レート制限 (Quota) の可視化**:
  - API から返されるクォータ情報（Remaining calls 等）をログに含め、枯渇の予兆を検知する。

## 3. エラー重要度 (Severity) の導入と通知チャネルの分離

### 現状の問題
- 現在は全てのエラーを一律「ERROR」として扱っており、システム異常（DBダウン）とユーザー側の問題（不正なファイル形式）の区別がついていない。
- これにより、開発者が通知過多（アラート疲れ）になる一方で、重大なインフラ障害の検知が遅れるリスクがある。

### 改善方針
- **エラーレベルの定義**:
  - **WARN**: 処理継続可能。ユーザー通知なし、ログのみ。
  - **ERROR**: ジョブ単位の失敗。ユーザー（Firestore）へ通知。開発者は統計として確認。
  - **CRITICAL**: システム全般の障害。開発者へ即時通知（Slack/PagerDuty等）。
- **判定ロジックの共通化**:
  - `domain` パッケージにベースとなるエラー（`ErrCritical`, `ErrJobError` 等）を定義し、`errors.Is` でレベルを判定可能にする。
- **通知チャネルのルーティング**:
  - `jobstatus.Notifier` 内部、または上位の `AlertManager` でレベルに応じて配送先（Firestore, Slack, Cloud Monitoring）を自動で切り替える。

## 4. ユーティリティ・ストレージ層の「隠蔽」の排除

### 現状の問題
- `util.MustJSON` がマーシャリング失敗時に `{}` を返し、エラーを握りつぶしている。
- `storage` 層の一部で文脈のないエラーが返されている。

### 改善方針
- **「Must」系の廃止**: エラーを握りつぶすユーティリティを避け、明示的に `error` を返すメソッドに置き換える、あるいは呼び出し側で `panic` させる（本当に不変な前提の場合）。
- **構造化された文脈**: エラー発生時に `document_id` 等の識別子を付加し、ログから影響範囲を特定しやすくする。
