# Worker Storage & Caching Contract

このドキュメントは、LLM Worker がファイルを保存・キャッシュする際の「契約（Contract）」を定義する。
これらのルールは、データの整合性を保ち、OOM を防ぎ、後続のジョブが安全にキャッシュを再利用するために厳守されなければならない。

## 1. GCS FUSE マウントの基本構造

Worker は GCS バケットをローカルファイルシステムとしてマウントし、以下の構造でデータを扱う。

```text
/mnt/gcs/
├── {workspace_id}/
│   ├── {document_id}                # 単一ファイルドキュメント本体 (ReadOnly)
│   └── {document_id}/               # ZIP展開後のドキュメント群 (ReadOnly)
└── .cache/
    └── v1/                          # キャッシュスキーマバージョン
        └── {document_id}/
            └── {doc_hash}/          # コンテンツハッシュによる世代管理
                ├── grep/
                │   └── {pattern_hash}.json  # grep 結果のキャッシュ
                ├── fts/
                │   └── bleve.index/         # 転置インデックス (Full Text Search)
                └── chunks.json              # 構造化済み中間データ
```

## 2. 世代管理と Invalidation のルール

- ドキュメントが更新・上書きされた場合でも、安全に処理を分離するため、キャッシュのパスには必ず `{doc_hash}` を含めること。
- **`doc_hash` の計算:**
  - 単一ファイルの場合: ファイル内容の SHA-256。
  - ZIPアーカイブの場合: 展開後のファイル群ではなく、**ZIPファイル自体の SHA-256** を使用する。
- **Invalidation:** アプリケーション側での明示的な削除は行わない。古いハッシュのディレクトリは GCS のライフサイクルルール（例：30日未アクセスで削除）に任せる。

## 3. アトミック書き込みのルール

GCS FUSE の性質上、複数ワーカーの書き込み競合を防ぐため、キャッシュやインデックスの作成時はアトミックな操作を徹底すること。

1. **Temp File への書き込み:** 処理中のデータは必ず `{filename}.tmp` 等の別名で書き切る。
2. **Rename 操作:** 書き込み完了後、OSの `rename` (`mv`) 操作で正規のファイル名に変更する。
3. **Last-writer-wins:** 完全に同時の書き込みが発生した場合、ロックは行わず「最後に rename したものが勝つ（上書きされる）」という方針を許容する（ハッシュが同じなら結果も同じはずであるという前提）。

## 4. 読み込み戦略 (Read-Through)

ツールがデータを必要とする場合、以下の順序でアクセスすること。

1. **キャッシュの確認:** 要求された処理結果（grep等）が `.cache/...` に存在するか確認する。
2. **キャッシュヒット:** 存在すればそれを読み込み、即座に終了する。
3. **キャッシュミス:** 存在しなければ、実データ（`/{workspace_id}/{document_id}`）に対して処理を行い、結果をテンポラリファイルに書き込んだ後、正規のキャッシュパスに Rename する。
